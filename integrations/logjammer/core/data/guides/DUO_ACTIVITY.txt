# DUO_ACTIVITY Log Generation Playbook

## 1. Overview & Log Purpose
`DUO_ACTIVITY` logs (also known as Duo Administrator Activity logs) are generated by the Cisco Duo Security Cloud Authentication Platform via the Duo Admin API (`/admin/v1/logs/administrator`). 

These audit logs record all identity, administrative, and configuration activities performed within the Duo Admin Panel or initiated by users and administrators via API integrations and self-service portals.

### Primary Activities Recorded
* **Authentication Management & Bypasses**: Creation, deletion, and usage of emergency bypass codes (`bypass_create`, `bypass_delete`).
* **Device & Credential Management**: Phone creation/updates, Duo Mobile activations, WebAuthn/FIDO2 security key registration, hardware token assignments, and device change verification responses (`phone_create`, `phone_associate`, `admin_activate_duo_push`, `webauthncredential_create`, `device_change_notification_answered`).
* **Security & Access Policy Administration**: Creation, modification, and assignment of global and application-specific access policies (`policy_create`, `policy_update`, `integration_policy_assign`).
* **Application Integrations & Secrets Access**: Creation, reconfiguration, and secret key viewing of protected application integrations (`integration_create`, `integration_update`, `integration_skey_view`).
* **Administrator Identity Lifecycle**: Administrator logins, privilege modifications, and administrative unit reassignments.

---

## 2. Format Specification

| Attribute | Specification |
| :--- | :--- |
| **Data Format** | Single-line JSON (JSON Lines / NDJSON) |
| **Character Encoding** | UTF-8 |
| **Quoting & Serialization** | Standard JSON double quotes (`"`). Nested metadata in `actor.details`, `action.details`, `old_target.details`, and `target.details` are serialized as **escaped JSON strings** (e.g., `"{\"key\": \"value\"}"`). |
| **Null Representation** | Explicit JSON `null` literal for unpopulated or non-applicable fields. |

---

## 3. Schema Breakdown & Fields

### Top-Level Schema

| Field Name | Type | Description | Mandatory | Example |
| :--- | :--- | :--- | :---: | :--- |
| `ts` | String | ISO 8601 UTC timestamp with microsecond resolution. | Yes | `2024-08-08T08:48:41.694670+00:00` |
| `activity_id` | String | Unique identifier (UUIDv4) for the activity event. | Yes | `b3dbf0ea-7b67-491a-bf02-3cdf6a80cb63` |
| `akey` | String | Duo Customer Account Key (starts with `DA`, 20 alphanumeric chars). | Yes | `DAXNJXBLBFXEVSYWCCO3` |
| `action` | Object | Details of the action performed. | Yes | `{"name": "bypass_create", "details": null}` |
| `actor` | Object | The entity (admin or user) executing the action. | Yes | See Actor Schema. |
| `access_device` | Object | Endpoint and network context of the actor initiating the action. | Yes | See Access Device Schema. |
| `application` | Object / null | Target Duo application integration (if applicable). | No | `{"key": "DIC4PZEQ2AXLTSBLPYAE", "name": "Admin API", "type": "adminapi"}` |
| `target` | Object / null | Object being acted upon (policy, user, phone, key, etc.). | No | See Target Schema. |
| `old_target` | Object / null | State of the target object prior to modification (used in updates). | No | See Target Schema. |
| `outcome` | String / null | Action outcome status (`null`, `"success"`, `"failure"`). | No | `null` |

### Nested Object Definitions

#### 1. `access_device` (Object)
Captures the client environment initiating the administrative request.
* `browser` (String): e.g., `"Chrome"`, `"Edge Chromium"`, `"Firefox"`, `"Safari"`, `"Unknown"`.
* `browser_version` (String): e.g., `"127.0.0.0"`, `""`.
* `ip` (Object):
  * `address` (String): Public or internal IPv4/IPv6 address.
* `location` (Object): Geo-location metadata.
  * `city` (String): e.g., `"Riverside"`, `"Ahmedabad"`, `"Austin"`.
  * `state` (String): e.g., `"California"`, `"Gujarat"`, `"Texas"`.
  * `country` (String): ISO/Full country name (e.g., `"United States"`, `"India"`).
* `os` (String): Client OS (`"Windows"`, `"Android"`, `"iOS"`, `"macOS"`, `"Linux"`).
* `os_version` (String): e.g., `"10"`, `"11"`, `"13"`, `"14.5"`.

#### 2. `action` (Object)
* `name` (String): The action verb. Common actions:
  * `admin_activate_duo_push`
  * `admin_login`
  * `bypass_create`, `bypass_delete`
  * `device_change_notification_answered`
  * `integration_create`, `integration_update`, `integration_delete`, `integration_policy_assign`, `integration_skey_view`
  * `phone_create`, `phone_update`, `phone_delete`, `phone_associate`, `phone_activation_code_regenerated`
  * `policy_create`, `policy_update`, `policy_delete`
  * `user_create`, `user_update`, `user_delete`
  * `webauthncredential_create`, `webauthncredential_delete`
* `details` (String / null): Escaped JSON string containing supplemental context (e.g., associations).

#### 3. `actor` (Object)
* `key` (String / null): Duo admin/user unique identifier (e.g., `"DU..."` or internal ID).
* `name` (String): Username, admin handle, or email address.
* `type` (String): `"admin"` or `"user"`.
* `details` (String): Escaped JSON string containing account metadata:
  * `created` (ISO 8601 String / null)
  * `last_login` (ISO 8601 String / null)
  * `email` (String / null)
  * `status` (String / null): e.g., `"Active"`, `"Disabled"`, `null`
  * `groups` (Array / null): Associated group names or IDs.

#### 4. `target` & `old_target` (Object)
* `key` (String / null): Unique ID of the object acted upon.
* `name` (String): Descriptive name, phone number, policy title, or identifier.
* `type` (String): Type of object:
  * `"user_bypass"`
  * `"phone"`
  * `"device_activity_notification"`
  * `"integration"`
  * `"policy"`
  * `"webauthn_credential"`
  * `"user"`
  * `"group"`
* `details` (String / null): Escaped JSON string containing detailed object schema and attributes.

---

### Duo Identifier Prefixes (20 Alphanumeric Characters)
Duo resource identifiers strictly adhere to known prefixes:
* `DA...` : Customer Account / Organization Key (`akey`)
* `DI...` : Integration Key / Application Key (`ikey` / `application.key`)
* `DU...` : User Key (`user.key`)
* `DP...` : Phone / Hardware Device Key (`phone.key`)
* `DB...` : Bypass Code Key (`bkeys`)
* `PO...` : Policy Key (`policy_key`)
* `WA...` : WebAuthn / Security Key Key (`webauthnkey`)

---

## 4. Timestamp & Dynamic Time Templating

Duo activity timestamps use UTC ISO 8601 notation with microsecond precision and an explicit `+00:00` offset:
`YYYY-MM-DDTHH:MM:SS.ffffff+00:00`

### Dynamic Time Tags for Synthetic Generation
* Main event timestamp: `##$TimeStamp-0d0h0m0s$##` (formatted as ISO 8601 `YYYY-MM-DDTHH:MM:SS.ffffff+00:00`)
* Actor creation timestamp: `##$TimeStamp-30d0h0m0s$##`
* Actor last login timestamp: `##$TimeStamp-0d1h15m0s$##`

## 6. Key Constraints & Pitfalls

1. **Nested Stringified JSON Fields**:
   * Fields `actor.details`, `action.details`, `old_target.details`, and `target.details` are JSON-encoded strings inside the parent JSON object. All internal quotes must be escaped (`\"`).
   * Failure to escape internal quotes properly results in invalid JSON and causes SIEM parser drops.

2. **Duo Prefix Integrity**:
   * Always match the field to its required prefix (`DA` for account/admin keys, `DI` for integrations/apps, `DU` for users, `DP` for phones, `DB` for bypass codes, `PO` for policies, `WA` for WebAuthn keys).

3. **Actor Representation Variances**:
   * For administrator actions: `actor.type` is `"admin"`, `actor.name` is the admin email/username, and `actor.key` is populated.
   * For user self-service actions: `actor.type` is `"user"`, `actor.name` is the user email, and `actor.key` is populated.
   * For automated activations or notifications: `actor.key` may be `null` and `actor.name` may be empty `""`.

4. **Required Root Keys**:
   * SIEM ingest parsers expect all top-level keys (`access_device`, `action`, `activity_id`, `actor`, `akey`, `application`, `old_target`, `outcome`, `target`, `ts`) to exist on every event, even if their values are `null`. Do not omit keys.

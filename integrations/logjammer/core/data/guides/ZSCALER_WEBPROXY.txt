# AI Generation Playbook: ZSCALER_WEBPROXY (Zscaler Internet Access NSS Web Logs)

---

## 1. Overview & Log Purpose

### System & Device Classification
* **Vendor**: Zscaler
* **Product**: Zscaler Internet Access (ZIA) / Nanolog Streaming Service (NSS)
* **Log Category**: Web Proxy & Secure Web Gateway (SWG) Access Logs
* **Sourcetype Variants**: `zscalernss-web`, `zscaler:zia:web`, `zscaler-nss`

### Activity Recorded
Zscaler NSS Web Proxy logs capture real-time HTTP, HTTPS, SSL/TLS, and DNS-over-HTTPS (DoH) transactions processed by the Zscaler cloud enforcement nodes. These logs document:
* **Web Traffic & Policy Enforcement**: URL categorization, allow/block decisions, bandwidth limits, cloud app usage.
* **Security & Threat Prevention**: Known malware downloads, botnet callback prevention, malicious IP/domain blocks, phishing prevention, cloud sandbox quarantine events.
* **Data Loss Prevention (DLP)**: Dictionary matches, pattern hits, file upload/download enforcement.
* **SSL/TLS Inspection**: Certificate verification, protocol inspection, cipher suite negotiation, SSL handshake failures, and inspection bypasses.
* **User & Device Telemetry**: User identity (UPN/email/machine accounts), source network location, Zscaler Client Connector (ZCC) device metadata, and OS environment.

## 2. Format Specifications

Zscaler NSS feeds can output logs in several standard formats depending on the SIEM integration profile. When generating synthetic logs, adhere strictly to one of the following primary formats.

### Format A: Splunk HEC / JSON Wrapper (Most Common)
Single-line JSON wrapped in an event envelope or emitted as a raw JSON payload.
* **Structure**: `{"event": { <key-value pairs> }, "sourcetype": "zscalernss-web"}`
* **Quoting & Types**: All keys and string values are double-quoted. Numeric values (sizes, status codes, risk scores) are commonly formatted as double-quoted strings in standard NSS templates (`"status": "200"`, `"pagerisk": "0"`).
* **Escaping**: Standard JSON escaping (`\"`, `\\`, `\n`).

### Format B: LEEF 1.0 (Log Event Extended Format over Syslog)
Used natively for IBM QRadar and standard Syslog collectors.
* **Structure**: `<PRI>MMM DD HH:MM:SS <Host> zscaler-nss: LEEF:1.0|Zscaler|NSS|<Version>|<Reason/Policy>|cat=<Action>\t<Key1>=<Val1>\t<Key2>=<Val2>...`
* **Delimiter**: Header fields are pipe-delimited (`|`); payload attributes are strictly tab-delimited (`\t`).
* **Header Fields (7 elements)**:
  `LEEF:Version|Vendor|Product|ProductVersion|EventID/Reason|cat=Action`

### Format C: Key-Value (KV) Tab-Delimited
Custom NSS stream emitting a timestamp prefix followed by tab-separated pairs.
* **Structure**: `YYYY-MM-DD HH:MM:SS [Timezone]\tkey1=value1\tkey2=value2\t...`
* **Delimiter**: Tab (`\t`) between key-value pairs; unquoted values unless strings contain explicit quotes.

### Format D: CEF (Common Event Format)
* **Structure**: `MMM DD HH:MM:SS <Host> CEF:0|Zscaler|NSSWeblog|<Version>|<DeviceEventClassID>|<Name>|<Severity>|act=<Action> app=<Protocol> ...`
* **Delimiter**: Space-separated `key=value` with standard CEF extension escaping.

## 4. Policy Action & Reason Matrix

When generating realistic logs, pair `action`, `reason`, and `status` according to this matrix:

| Scenario | Action (`action` / `cat`) | Reason (`reason` / `policy`) | Status (`status` / `respcode`) | Protocol / Method |
| :--- | :--- | :--- | :--- | :--- |
| **Normal Allowed Web** | `Allowed` | `Allowed` | `200`, `201`, `204`, `302` | `HTTPS` / `GET`, `POST` |
| **SSL Proxy Connect** | `Allowed` | `Allowed` | `200` | `HTTP_PROXY` / `CONNECT` |
| **URL Category Block** | `Blocked` | `Not allowed to browse this category` | `403` | `HTTP`, `HTTPS` / `GET`, `POST` |
| **Firewall Rule Block** | `Blocked` | `Web application is blocked by Firewall rule` | `403` | `HTTP` / `GET` |
| **SSL Handshake Drop** | `Blocked` | `Dropped due to failed client SSL handshake` | `NA` | `SSL` / `NA` |
| **Bad Server Cert** | `Blocked` | `Access denied due to bad server certificate` | `403` | `HTTPS` / `POST`, `GET` |
| **Botnet / Malware Hit**| `Blocked` | `Reputation block outbound request: botnet site` | `403` | `HTTP` / `CONNECT`, `GET` |
| **Country Geo-Block** | `Blocked` | `Country block outbound request: not allowed to access sites in this country` | `NA` | `SSL` / `NA` |
| **Sandbox Quarantine** | `Blocked` / `Quarantined` | `Quarantined` | `403` | `HTTPS` / `GET` |
| **DLP Block** | `Blocked` | `Blocked by DLP policy violation` | `403` | `HTTPS` / `POST`, `PUT` |

## 5. Timestamp & Dynamic Time Templating

Zscaler NSS uses different time formats based on the log transmission layer:
* **JSON NSS**: `YYYY-MM-DD HH:MM:SS` (field `datetime`) and Unix Epoch seconds (field `epochtime`).
* **JSON ZIA v1.4+**: ISO 8601 UTC `YYYY-MM-DDTHH:MM:SSZ` (field `datetime`) and Unix Epoch seconds (field `edatetime`).
* **LEEF Header Syslog**: Standard BSD Syslog timestamp `MMM dd HH:mm:ss`.
* **LEEF `devTime` Parameter**: `MMM dd yyyy HH:mm:ss z` (e.g., `May 27 2024 14:29:39 America/New York` or `GMT`).

### Required Dynamic Time Template Tags
When generating scenario logs, use the following dynamic replacement tags:

* Standard Date/Time (`datetime`): `##$TimeStamp-0d2h15m0s$##` -> `2024-05-06 10:56:04`
* ISO 8601 UTC: `##$Iso8601-0d2h15m0s$##` -> `2024-05-06T10:56:04Z`
* Epoch Seconds (`epochtime`, `edatetime`): `##$Epoch-0d2h15m0s$##` -> `1714992964`
* Syslog Header Time: `##$SyslogTime-0d2h15m0s$##` -> `May  6 10:56:04`
* Custom Time for LEEF `devTime`: `##$CustomTime:MMM dd yyyy HH:mm:ss-0d2h15m0s$## America/New York` -> `May 06 2024 10:56:04 America/New York`

## 7. Key Constraints & Common Pitfalls

### Mandatory Parsing Rules
1. **LEEF Tab Delimiter**: In LEEF logs, the attributes *must* be separated by the literal horizontal tab (`\t`) character. Using spaces between key-value pairs will cause QRadar and generic syslog parsers to fail.
2. **Missing/Null Field Values**: Zscaler NSS does not use empty strings or JSON `null` for unpopulated attributes. It outputs literal `"None"`, `"NA"`, `"N/A"`, or `"0"` depending on the field.
   * `threatname`: `"None"`
   * `requestmethod`: `"NA"` (for lower-level SSL/TLS records before HTTP decapsulation)
   * `status`: `"NA"` (when no HTTP response was sent, e.g., dropped TCP connection)
   * `pagerisk` / `riskscore`: `"0"`
3. **URL Encoding Consistency**: Field values containing spaces—such as `department`, `location`, `urlcategory`, and `useragent`—are frequently URL-encoded (`%20`) by NSS depending on feed configuration (`Road%20Warrior` vs `Road Warrior`).
4. **URL vs. Hostname**:
   * `hostname`: Pure FQDN or IP without scheme or port (e.g., `login.microsoft.com`).
   * `url`: Full path or host with explicit port (e.g., `login.microsoft.com:443` or `example.com/api/v1/auth?client_id=123`).
5. **Byte Consistency**:
   * Ensure `transactionsize` roughly equals `requestsize` + `responsesize`.
   * For blocked requests at the TCP/SSL level, `requestsize` may be small (handshake size) and `responsesize` is typically `0`.
   * For proxy `CONNECT` tunnels, `responsesize` is commonly small (e.g., `65` bytes representing HTTP 200 Connection Established).

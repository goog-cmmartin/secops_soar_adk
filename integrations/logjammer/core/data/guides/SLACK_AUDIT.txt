# Comprehensive Log Generation Playbook: Slack Audit Logs (`SLACK_AUDIT`)

---

## 1. Overview & Log Purpose

### Description
Slack Audit Logs are generated by the **Slack Enterprise Grid Audit Logs API** (`/api/v1/logs`). They record an immutable, auditable trail of security, configuration, and user events across an entire Slack Enterprise organization and its underlying workspaces.

### Operational Context
Enterprise security teams, Security Operations Centers (SOCs), and Detection Engineering pipelines ingest Slack Audit logs to monitor:
- **User Authentication & Lifecycle**: Logins, logouts, session timeouts, role updates, deactivations, MFA/SSO interactions.
- **Data Access & Exfiltration**: Large-scale file downloads, unauthorized file sharing, public link generation.
- **Channel Operations**: Creation, archiving, conversions between private/public, cross-workspace channel sharing (Slack Connect).
- **Administrative & Security Operations**: App installation, OAuth scope escalation, DLP/EKM events, Enterprise Grid policy alterations.
- **Automated Anomaly Detection**: Slack native security detection events (e.g., impossible travel, brute-force patterns, excessive downloads).

## 2. Format Specification

### Format Classification
- **Native Structure**: Hierarchical **JSON (JavaScript Object Notation)**.
- **Ingestion/Transport Format**: **NDJSON (Newline-Delimited JSON)** where each audit event is a single-line JSON string, or framed JSON arrays collected via REST API polling.
- **Character Encoding**: UTF-8.

### Delimiters and Quoting Rules
- **Keys and String Values**: Wrapped in standard double quotes (`"`).
- **Arrays**: Standard bracket notation (`[...]`).
- **Null Values**: Unquoted literal `null`.
- **Numbers / Timestamps**: Unquoted integers / floats.
- **Escaping**: Standard JSON escaping rules apply:
  - Quotes inside strings must be escaped: `\"`
  - Backslashes: `\\`
  - Control characters (`\n`, `\r`, `\t`) must be escaped if embedded.

### ID Prefix Conventions (Slack Entity Standards)
Slack uses structured alphanumeric prefixes across identifiers:
- `E...` : Enterprise Organization ID (e.g., `E01JHFK2BF0`)
- `T...` : Workspace / Team ID (e.g., `T024FA1UX`, `T0196UXK57B`)
- `U...` or `W...` : User ID (e.g., `U01R6G7LBKK`, `W012NMGKUDB`)
- `C...` : Public/Private Channel ID (e.g., `C02GAJ1D75W`)
- `G...` : Multi-party Direct Message (MPDM) / Group / Shared Channel ID (e.g., `GA3DDRVH6`)
- `F...` : File ID (e.g., `F02F67XQP63`, `F07N4MHUFE3`)
- `R...` : Huddle / Call ID (e.g., `R02FZH6BJUR`)
- `A...` / `B...` : App / Bot ID (e.g., `A020K3U2KM0`, `B01JHFK2BF0`)

## 3. Schema Breakdown & Fields

### Top-Level JSON Schema

```json
{
  "id": "String (UUIDv4)",
  "date_create": "Integer (Unix Epoch Seconds)",
  "action": "String (Action Identifier)",
  "actor": {
    "type": "String (user | app | bot | workflow)",
    "user": {
      "id": "String (Slack User ID)",
      "name": "String (User Display/Real Name)",
      "email": "String (RFC 5322 Email)",
      "team": "String (Slack Team/Org ID)"
    }
  },
  "entity": {
    "type": "String (user | file | channel | huddle | app | workspace | enterprise)",
    "<entity_type_key>": { ... }
  },
  "context": {
    "location": {
      "type": "String (workspace | enterprise)",
      "id": "String (Slack ID)",
      "name": "String (Workspace/Org Name)",
      "domain": "String (Workspace/Org Subdomain)"
    },
    "ua": "String (User Agent)",
    "ip_address": "String (IPv4 or IPv6)",
    "session_id": "Integer (Int64) | null"
  },
  "details": {
    "...": "Action-specific fields"
  }
}
```

---

### Detailed Field Definitions

| Field Path | Type | Nullable | Description & Expected Values |
| :--- | :--- | :--- | :--- |
| `id` | String | No | Unique Event UUIDv4 (e.g., `8aad5d27-5a5c-4f69-867b-4580e48d6732`). |
| `date_create` | Integer | No | Unix Epoch timestamp in **seconds** (e.g., `1738839878`). |
| `action` | String | No | The action performed. See *Action Verbs* below. |
| `actor.type` | String | No | Category of caller: `user`, `app`, `bot`, `workflow`, `system`. |
| `actor.user.id` | String | No | Slack User ID of the initiator (`U...` or `W...`). |
| `actor.user.name` | String | No | Full display or username (e.g., `Alice Smith`, `bot-github`). |
| `actor.user.email` | String | No | Valid email (e.g., `alice@example.com`, `botuser-T01...-A01...@slack-bots.com`). |
| `actor.user.team` | String | No | Home Team ID (`T...`) or Enterprise ID (`E...`). |
| `entity.type` | String | No | Target entity type: `file`, `channel`, `user`, `huddle`, `workspace`, `app`, `workflow`, `barrier`. |
| `entity.<type>` | Object | No | Key matches `entity.type` containing child properties (e.g., `entity.file`, `entity.channel`). |
| `context.location.type` | String | No | Location tier: `workspace` or `enterprise`. |
| `context.location.id` | String | No | Workspace ID (`T...`) or Enterprise ID (`E...`). |
| `context.location.name` | String | No | Display name of the workspace/enterprise. |
| `context.location.domain` | String | No | Subdomain (e.g., `acme`, `corp-eng`, `security-lab`). |
| `context.ua` | String | No | Client User Agent string. Empty `""` for some internal tasks/scripts. |
| `context.ip_address` | String | No | Valid public or private IPv4/IPv6 address. |
| `context.session_id` | Integer | Yes | 13-digit integer session ID (e.g., `2499920369271`) or `null` for non-interactive/bot actions. |
| `details` | Object | Yes | Action-dependent contextual data. Absent or present based on `action`. |

## 4. Timestamp & Dynamic Time Templating

### Format Reference
- **Top-Level (`date_create`)**: Unix Epoch in **seconds** (10-digit integer).
- **Details (`action_timestamp`)**: Unix Epoch in **microseconds** (16-digit integer).
- **Huddle (`date_start`, `date_end`)**: Unix Epoch in **seconds** (10-digit integer).

### Template Macro Tags
When generating synthetic scenarios, replace static epoch timestamps with dynamic time calculation macros:

- `##$Epoch-0d0h0m0s$##` : Current event timestamp in epoch seconds (e.g., `1738839878`).
- `##$Epoch-0d0h5m0s$##` : 5 minutes prior to the base timestamp (epoch seconds).
- `##$Epoch-0d2h0m0s$##` : 2 hours prior to the base timestamp (epoch seconds).
- `##$EpochMicro-0d0h0m10s$##` : Microsecond-level timestamp for `details.action_timestamp` (16 digits).

## 6. Key Constraints & Common Pitfalls

### Mandatory Parsing Dependencies
1. **`date_create` must be an unquoted integer**: Putting quotes around the epoch timestamp (`"1632515552"`) will cause ingestion parsing errors in SIEM schemas expecting a strict numerical timestamp.
2. **Synchronized Entity Types**: The key inside `entity` must match `entity.type`. If `entity.type` is `"file"`, the inner dictionary key must be `"file"`. If `"channel"`, it must be `"channel"`.
3. **Session ID Type Handling**:
   - Interactive user actions: 13-digit integer (e.g., `2499920369271` or `8269895388903`).
   - Bot, Webhook, or System actions: Must be literal `null`, **never** an empty string `""`.
4. **Identifier Consistency**:
   - Never generate mismatched identifiers (e.g., actor user ID starting with `C` or file ID starting with `U`).
   - User IDs: `U` or `W` prefix.
   - Channel IDs: `C` or `G` prefix.
   - File IDs: `F` prefix.
   - Team IDs: `T` prefix.
   - Enterprise IDs: `E` prefix.
5. **No SIEM Pre-Parser Pollution**:
   - Some collectors inject supplementary keys (such as `tag: "acme.slack"`, `Extracted_IPs: [...]`, or `count: 3`). When modeling canonical Slack audit events, ensure the core Slack API JSON schema remains standard.

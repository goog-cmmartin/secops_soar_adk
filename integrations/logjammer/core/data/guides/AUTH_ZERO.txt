# Detection Engineering Playbook: Auth0 (AUTH_ZERO) Identity & Access Logs

---

## 1. Overview & Log Purpose

**Auth0** (by Okta) is an Identity-as-a-Service (IDaaS) and Customer Identity and Access Management (CIAM) platform. Auth0 logs record all authentication, authorization, user management, and administrative actions occurring across applications, identity providers (IdPs), APIs, and the Auth0 Management API.

### Core Activities Logged
* **User Authentication & Authorization**: Interactive web logins, single sign-on (SSO), social logins (Google, Apple, Microsoft), enterprise federation (SAML, WS-Fed, Azure AD/WAAD), and passwordless authentication (SMS, Magic Links).
* **Token Operations**: OAuth 2.0 / OpenID Connect (OIDC) token exchanges, authorization code grants, client credential flows (M2M), refresh token exchanges, and token revocation.
* **Security & Adaptive MFA**: Pre-login risk assessments, anomaly detection (impossible travel, untrusted IP, brute force protection), and MFA challenges/enrollments.
* **Management API Auditing**: Administrative and automated configuration changes via the Management API v2 (e.g., user provisioning, role assignments, client creation, secret access, tenant configuration modifications).
* **Notification Deliveries**: System emails and SMS delivery tracking (verification emails, password reset links).

---

## 2. Format Specification

### Structural Models
Auth0 emits logs in **JSON format**. Depending on the delivery mechanism (Auth0 Log Streaming, Log Streams to AWS EventBridge/Datadog/Splunk, Management API `/api/v2/logs` polling, or SIEM webhooks), logs appear in one of three structural envelopes:

1. **Standard / Flat JSON** (Direct API export or legacy syslog/HTTP export):
   ```json
   {
     "date": "2024-11-07T03:29:03.299Z",
     "type": "s",
     "description": "",
     "client_id": "...",
     "ip": "...",
     "details": { ... },
     "log_id": "90020241107032903328307000000000000001223372061753965617"
   }
   ```

2. **Stream Data Wrapper** (Auth0 Log Stream / Event Stream payload):
   ```json
   {
     "log_id": "90020241107032903328307000000000000001223372061753965617",
     "data": {
       "date": "2024-11-07T03:29:03.299Z",
       "type": "s",
       "details": { ... }
     }
   }
   ```

3. **AWS EventBridge Partner Wrapper** (When routed via AWS Partner Event Source):
   ```json
   {
     "version": "0",
     "id": "357f9ed5-c60d-6eca-afff-ea8af3559b4e",
     "detail-type": "Auth0 log",
     "source": "aws.partner/auth0.com/tenant-name/auth0.logs",
     "account": "123456789012",
     "time": "2024-08-01T18:56:15Z",
     "region": "us-east-1",
     "resources": [],
     "detail": {
       "log_id": "...",
       "data": { ... }
     }
   }
   ```

### Delimiters & Escaping Rules
* **Encoding**: UTF-8.
* **Strings & Nested Structures**: JSON-escaped strings (`\"`). Complex nested payloads (such as user metadata or HTTP request bodies) are serialized as nested JSON objects or JSON-encoded strings inside metadata.
* **Sensitive Value Masking**: Auth0 automatically masks sensitive fields with asterisks:
  * Passwords: `"password": "*****"`
  * Authorization Codes: `"code": "******************************************7bT"`
  * User Verification Codes: `"verification_code": "******"`

## 3. Schema Breakdown & Fields

### 3.1 Event Type Codes (`type`)
The `type` field is the primary indicator of the event action.

| Type Code | Description | Category | Severity / Security Impact |
| :--- | :--- | :--- | :--- |
| `s` | Successful Login | Authentication | Informational |
| `f` | Failed Login | Authentication | Warning / Potential Brute Force |
| `ss` | Successful Signup | Registration | Informational |
| `fs` | Failed Signup | Registration | Warning |
| `slo` | Successful Logout | Session | Informational |
| `flo` | Failed Logout | Session | Warning |
| `scp` | Successful Change Password | Account Management | Informational (Audit trail) |
| `fcp` | Failed Change Password | Account Management | Warning |
| `fcpr` | Failed Change Password Request | Account Management | Warning (User enumeration) |
| `sdu` | Successful User Deletion | Account Management | Medium / Data lifecycle |
| `fdu` | Failed User Deletion | Account Management | Warning |
| `seacft` | Success Exchange Authorization Code for Access Token | OAuth / OIDC | Informational |
| `feacft` | Failed Exchange Authorization Code for Access Token | OAuth / OIDC | Warning / Potential replay |
| `seccft` | Success Exchange Client Credentials for Access Token | OAuth / M2M | Informational |
| `feccft` | Failed Exchange Client Credentials for Access Token | OAuth / M2M | Warning / Auth failure |
| `sertft` | Success Exchange Refresh Token for Access Token | OAuth / OIDC | Informational |
| `fertft` | Failed Exchange Refresh Token for Access Token | OAuth / OIDC | High (Token replay / theft indicator) |
| `fsa` | Failed Silent Authentication | Authentication | Warning / Session expired |
| `pla` | Pre-login Risk Assessment | Anomaly Detection | Informational / Contextual |
| `cls` | Passwordless Code / Link Sent | Passwordless | Informational |
| `fn` | Failed Notification / Email Delivery | System / Delivery | Warning |
| `sapi` | Success Management API v2 Operation | Admin / Management | Informational / High Audit |
| `fapi` | Failed Management API v2 Operation | Admin / Management | Warning / High Audit |
| `mgmt_api_read` | Management API Read Operation | Admin / Management | Informational (Data discovery) |
| `api_limit` | Tenant Rate Limit Exceeded | Platform | High / DoS / Throttle |
| `depnote` | Feature Deprecation Notice | System | Informational |

## 4. Timestamp & Dynamic Time Templating

Auth0 logs contain two distinct time representations:
1. **Primary ISO 8601 UTC Timestamp (`date`)**: String format `YYYY-MM-DDTHH:MM:SS.sssZ`.
2. **Prompts & Execution Milliseconds (`initiatedAt`, `completedAt`)**: 13-digit Unix Epoch Milliseconds integer.

### Relative Time Template Tags
When generating synthetic logs, always ensure temporal synchronization between the root ISO string and the nested epoch millisecond timestamps:

* **ISO 8601 String**: `##$TimeStamp-0d0h0m0s$##` (Evaluates to `YYYY-MM-DDTHH:MM:SS.sssZ`)
* **Epoch Milliseconds**: `##$EpochMs-0d0h0m0s$##` (Evaluates to 13-digit integer, e.g., `1722516274732`)
* **Epoch Seconds**: `##$Epoch-0d0h0m0s$##` (Evaluates to 10-digit integer, e.g., `1722516274`)

## 6. Key Constraints & Pitfalls

### Critical Schema Dependencies
* **Monotonic Log ID Structure**: `log_id` is an essential deduplication key in SIEM pipelines (Splunk, Elastic, Sentinel). It begins with `900` followed by the date string representation and high-precision event counters (`900YYYYMMDD...`). If constructing an event wrapper, `log_id` MUST be identical at the wrapper root and within `data.log_id`.
* **String vs. Array Scopes**: The `scope` parameter can be a space-delimited string (`"openid profile email"`) or an array of strings (`["openid", "profile"]`). Parsers must handle both types.
* **Blank vs Null Strings**: In unauthenticated failures or machine-to-machine operations, `user_id` and `user_name` are represented as empty strings (`""`) rather than `null`.
* **Event Structure Consistency**: When generating event streams, do not mix root-level fields with wrapper models inside the same stream unless testing heterogeneous ingest pipelines. Choose either the Flat model or the `{"log_id": "...", "data": { ... }}` model consistently per generated batch.
* **Exclude Extraneous CDN Noise**: Edge CDN logs (e.g., Cloudflare HTTP request logs with `RayID`, `EdgeResponseStatus`) must NOT be merged into Auth0 authentication records. Auth0 emits solely its application/identity event structure.

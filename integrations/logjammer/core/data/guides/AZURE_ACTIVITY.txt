# AI Generation Playbook: Azure Activity Logs (`AZURE_ACTIVITY`)

---

## 1. Overview & Log Purpose

### Log Source Description
Azure Activity Logs (formerly Azure Audit Logs) record subscription-level control-plane events across Microsoft Azure. They capture actions taken on resources—such as resource creation, updates, deletions, role assignments, security alerts, and health state transitions—initiated via the Azure Portal, PowerShell, Azure CLI, REST API, or internal Azure platform services.

### Core Activities Logged
- **Administrative**: CRUD operations on Azure Resource Manager (ARM) resources (e.g., `Microsoft.Compute/virtualMachines/write`, `Microsoft.Storage/storageAccounts/listKeys/action`, `Microsoft.Authorization/roleAssignments/write`).
- **Security**: Alerts and recommendations generated by Microsoft Defender for Cloud / Azure Security Center.
- **Resource Health**: Platform-initiated and user-initiated health events affecting resource availability.
- **Alert / Autoscale / Policy**: Resource metric alert firings, autoscaling actions, and Azure Policy non-compliance/audit events.
- **Service Health**: Service outages, planned maintenance, and advisory incidents.

---

## 2. Format Specification

### Classification
- **Syntax**: JSON (Newline Delimited JSON / NDJSON in streaming pipelines such as Azure Event Hubs, Azure Storage diagnostic export, or Azure Log Analytics).
- **Structure**: Flat key-value root paired with nested JSON objects (`identity`, `claims`, `authorization`, `properties`).
- **Quoting & Escaping**: Standard JSON rules apply. Internal nested JSON structures (e.g., `properties.requestbody`, `properties.statusMessage`, `properties.legacyEventProperties`) MUST be serialized as escaped JSON strings (`\"key\":\"value\"`).

### Nested Object: `properties`

The `properties` object structure varies by `category`:

#### 1. Administrative Events
- `eventCategory`: `"Administrative"`
- `entity`: Resource ID matching the targeted entity.
- `message`: Operation action name.
- `hierarchy`: Management group / subscription hierarchy path (e.g., `<tenantId>/<mgmtGroup>/<subId>`).
- `statusCode`: HTTP Response code (e.g., `"OK"`, `"Created"`, `"Accepted"`, `"BadRequest"`).
- `requestbody`: Escaped JSON string containing the ARM payload.
- `statusMessage`: Escaped JSON string containing error details if `resultType` is `"Failed"` or `"Failure"`.

#### 2. ResourceHealth Events
- `eventCategory`: `"ResourceHealth"`
- `eventProperties`:
  - `title`: Health summary (e.g., `"Reboot initiated from inside the machine"`, `"Unavailable"`).
  - `currentHealthStatus`: `"Available"`, `"Unavailable"`, `"Degraded"`, `"Unknown"`.
  - `previousHealthStatus`: `"Available"`, `"Unavailable"`, `"Degraded"`, `"Unknown"`.
  - `type`: `"Downtime"`, `"Degraded"`, `"Annotation"`.
  - `cause`: `"UserInitiated"`, `"PlatformInitiated"`, `"Unknown"`.

#### 3. Security (Defender for Cloud) Events
- `eventCategory`: `"Security"`
- `eventName`: Alert display name (e.g., `"Multiple Domain Accounts Queried"`, `"Suspicious Process Execution"`).
- `eventProperties`:
  - `compromisedHost`: Name of affected host.
  - `userName`: Targeted or executing user account.
  - `suspiciousProcess`: Binary path (`c:\\windows\\system32\\net.exe`).
  - `suspiciousCommandLine`: Full command line.
  - `severity`: `"Low"`, `"Medium"`, `"High"`, `"Informational"`.
  - `intent`: Array of ATT&CK tactics (e.g., `["Discovery"]`, `["Execution", "Persistence"]`).

## 4. Timestamp & Dynamic Time Templating

Azure Activity logs require ISO 8601 UTC timestamps at the root level and numeric Epoch seconds inside JWT token claims.

### Time Tag Formatting
- **Root Level (`time`)**: `YYYY-MM-DDTHH:MM:SS.SSSSSSSZ`
  - Template: `##$TimeStamp-0d0h0m0s$##` (Format: ISO 8601 UTC with milliseconds/nanoseconds).
- **Embedded JWT Claims (`iat`, `nbf`, `exp`)**:
  - `iat` (Issued At): `##$Epoch-0d1h0m0s$##`
  - `nbf` (Not Before): `##$Epoch-0d1h0m0s$##`
  - `exp` (Expiration): `##$Epoch-0d0h0m0s$##` (or future epoch).

## 6. Key Constraints & Pitfalls

1. **Mandatory Parser Keys**:
   - `time`, `resourceId`, `operationName`, `category`, `resultType`, `correlationId`, `level`, and `properties` must always be present. Dropping `correlationId` or `operationName` causes unparsed records in major SIEM parsers (e.g., Microsoft Sentinel, Splunk Azure Add-on).

2. **Escaping of Sub-JSON Properties**:
   - Fields such as `properties.requestbody`, `properties.statusMessage`, and `properties.legacyEventProperties` contain inner JSON strings.
   - **Incorrect**: `{"requestbody": {"name": "test"}}`
   - **Correct**: `{"requestbody": "{\"name\":\"test\"}"}`

3. **Case Sensitivity in Resource URIs**:
   - The root `resourceId` is often written in uppercase segments (`/SUBSCRIPTIONS/.../PROVIDERS/...`), but the internal path in `identity.authorization.scope` or `properties.entity` is lowercase or mixed camelCase. Ensure exact casing conventions match realistic outputs.

4. **Claim Field Naming**:
   - Standard claims are prefixed with Microsoft and SOAP XML schemas:
     - `http://schemas.microsoft.com/identity/claims/objectidentifier`
     - `http://schemas.microsoft.com/identity/claims/tenantid`
     - `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name`
     - `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/upn`
   - Do not replace these with short aliases (like `user_id` or `upn`) unless modeling custom token transformations.

5. **`durationMs` Data Types**:
   - In standard ARM administrative events, `durationMs` is commonly returned as a string (`"0"`, `"277"`). In service health/backup operations, it may appear as an integer (`0`). Maintain type consistency based on the operation category.

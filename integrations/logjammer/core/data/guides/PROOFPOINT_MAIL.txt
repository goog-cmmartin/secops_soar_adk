# Proofpoint Email Security (PROOFPOINT_MAIL) Log Generation Playbook

---

## 1. Overview & Log Purpose

**Proofpoint Email Security** generates events covering inbound, outbound, and internal email processing, threat detection, policy enforcement, and post-delivery URL click telemetry. The data originates from two primary architectures:

1. **Proofpoint Targeted Attack Protection (TAP) SIEM API**:
   - Pulls real-time detection intelligence regarding malicious messages and credential-phishing/malware URLs.
   - Categorizes events into four core telemetry streams:
     - `messagesBlocked`: High-risk or malicious messages quarantined/dropped at gateway.
     - `messagesDelivered`: Clean or policy-altered messages successfully passed to the destination mail server (e.g., Microsoft 365, Google Workspace, Exchange).
     - `clicksBlocked`: User clicks on rewritten URLs (URL Defense) that were blocked at click-time.
     - `clicksPermitted`: User clicks on rewritten URLs where the threat was weaponized post-delivery or permitted by policy.
2. **Proofpoint Protection Server (PPS) Enterprise Gateway Syslog**:
   - Streamed via RFC 3164 or RFC 5424 from physical/virtual appliances or hosted clusters (`pphosted.com`).
   - Details low-level SMTP filter stages (`filter_instance`), module execution (`spf`, `dkim`, `av`, `zerohour`, `spam`, `sandbox`, `urldefense`), and final MTA routing (`sendmail`).

---

## 2. Format Specification

Proofpoint events exist in two primary formats depending on the ingestion pipeline:

```
+------------------------------------+---------------------------------------------+
| Telemetry Type                     | Wire Format                                 |
+------------------------------------+---------------------------------------------+
| Proofpoint TAP SIEM REST API       | Minified / Formatted JSON (Batch Envelope)  |
| Proofpoint Protection Server (PPS) | Syslog (RFC 3164 / RFC 5424) + Key-Value   |
+------------------------------------+---------------------------------------------+
```

### 2.1 TAP SIEM API Format (JSON)
- **Root Object**: Top-level envelope containing batch arrays: `messagesBlocked`, `messagesDelivered`, `clicksBlocked`, `clicksPermitted`, and the query metadata field `queryEndTime`.
- **Delimiters & Quoting**: Standard RFC 8259 JSON.
- **Character Escaping**: RFC 822 email headers and IDs containing HTML angle brackets (`<`, `>`) and ampersands (`&`) in URLs are escaped via Unicode encoding (e.g., `\u003cabc@domain.com\u003e`, `\u0026id=...`).

### 2.2 PPS Appliance Syslog Format (Key-Value)
- **Syslog Envelope**: Standard BSD Syslog (RFC 3164) `<PRI>MMM DD HH:MM:SS host app[PID]:` or RFC 5424 `<PRI>YYYY-MM-DDTHH:MM:SS.ffffffZZ:ZZ host app[PID]:`.
- **Facility / Priority**:
  - `<141>` (local1.notice): Filter execution, disposition, and message reporting (`rprt`).
  - `<142>` (local1.info): Informational operational events (`info`).
  - `<140>` (local1.warning): Gateway warnings (`warn`).
  - `<139>` (local1.error): Gateway errors and encryption faults (`err`).
  - `<22>` (mail.info): MTA/Sendmail message transit, queues, and deferral statuses.
- **Message Payload**: Space-delimited `key=value` tokens. Values containing spaces, complex expressions, or URLs MUST be enclosed in double quotes (e.g., `subject="Invoice 123"`, `record="v=spf1 ..."`). Empty key-values end with an equals sign with no whitespace (`size= smtputf8=`).

## 3. Schema Breakdown & Fields

### 3.1 TAP JSON Fields

#### Top-Level Envelope
| Field | Type | Description |
| :--- | :--- | :--- |
| `queryEndTime` | String (ISO 8601) | Query execution/watermark timestamp (e.g., `2023-10-25T14:30:00Z`). |
| `messagesBlocked` | Array of Objects | Inbound messages blocked/quarantined by threat policies. |
| `messagesDelivered`| Array of Objects | Messages passed to downstream mail infrastructure. |
| `clicksBlocked` | Array of Objects | URL clicks terminated by URL Defense page blocks. |
| `clicksPermitted` | Array of Objects | URL clicks permitted through to the target destination. |

### 3.2 PPS Syslog Fields

#### Common PPS Syslog Header Tokens
- `s=<session_id>`: Alphanumeric session tracker (e.g., `3d3sasg9d2`).
- `m=<msg_num>`: Message index within the SMTP session (e.g., `1`).
- `x=<tracking_id>`: Composite transaction identifier (e.g., `3d3sasg9d2-1`).
- `mod=<module>`: Component emitting the log (`mail`, `session`, `spf`, `av`, `zerohour`, `spam`, `sandbox`, `smtpsrv`, `crypto`, `dkim`, `urldefense`, `filter`).
- `cmd=<action>`: Sub-routine executed (`env_from`, `data`, `headers`, `run`, `attachment`, `dispose`, `send`, `msg`, `stat`, `connect`, `starttls`).

#### Detailed Filter Module Key-Values
| Module (`mod`) | Key Attribute Pairs |
| :--- | :--- |
| `spf` | `result=pass\|fail\|softfail\|neutral\|none`, `record="v=spf1 ..."`, `dnsid=<int>`, `querydepth=<int>` |
| `dkim` | `cmd=run`, `domain=<str>`, `selector=<str>`, `result=pass\|fail`, `hfrom_domain=<str>` |
| `av` | `cmd=run`, `rule=clean\|infected`, `vendor=<engine>`, `version="definitions=..."`, `duration=<float>` |
| `zerohour` | `cmd=run`, `rule=none\|virus`, `virusthreat=unknown\|clean\|malware`, `virusthreatid="<id>"` |
| `spam` | `rule=inbound_bulk\|inbound_spam_definite\|inbound_phish`, `spamscore=<int>`, `phishscore=<int>`, `malwarescore=<int>`, `bulkscore=<int>`, `tests=<COMMA_SEPARATED_PROOFPOINT_RULES>`, `duration=<float>` |
| `sandbox` | `cmd=run`, `token="X-Proofpoint-TraceToken: ..."`, `msghold_response="verdict => PROCEED\|BLOCK"` |
| `session` | `cmd=dispose`, `module=<mod>`, `rule=<rule>`, `action=continue\|reject\|quarantine\|set-header\|add-header`, `value="..."` |
| `mail` | `cmd=msg`, `qid=<MTA_QID>`, `size=<int>`, `guid=<GUID>`, `hdr_mid=<Message-ID>`, `duration=<float>`, `elapsed=<float>` |

#### Sendmail MTA Key-Values
| Action Type | Syslog Line Format Key-Values |
| :--- | :--- |
| `Connect / TLS` | `STARTTLS=client\|server, relay=<fqdn>, version=TLSv1.2\|TLSv1.3, verify=OK\|NONE, cipher=<cipher>, bits=<int>` |
| `Incoming Envelope` | `<QID>: from=<<email>>, size=<bytes>, class=<int>, nrcpts=<int>, msgid=<<mid>>, proto=ESMTP, relay=<host> [<ip>]` |
| `Outbound Dispatch` | `<QID>: to=<<email>>, delay=HH:MM:SS, xdelay=HH:MM:SS, mailer=esmtp, tls_verify=OK, tls_version=TLSv1.2, cipher=<cipher>, pri=<int>, relay=<host> [<ip>], dsn=2.0.0\|4.2.2\|5.7.1, stat=Sent\|Deferred\|User unknown` |

## 4. Timestamp & Dynamic Time Templating

To support high-fidelity, dynamic log generation across diverse scenarios, use the following relative timestamp macros:

| Format Name | Specification | Generation Template Tag | Example Output |
| :--- | :--- | :--- | :--- |
| **TAP ISO 8601 Milliseconds** | `YYYY-MM-DDTHH:MM:SS.000Z` | `##$TimeStamp-0d2h15m0s$##` | `2023-10-25T12:45:00.000Z` |
| **TAP Query End Time** | `YYYY-MM-DDTHH:MM:SSZ` | `##$TimeStamp-0d0h0m0s$##` | `2023-10-25T15:00:00Z` |
| **BSD Syslog (RFC 3164)** | `MMM D HH:MM:SS` (space-padded day) | `##$SyslogTime-0d0h10m0s$##` | `Oct 25 14:50:00` |
| **RFC 5424 Timestamp** | `YYYY-MM-DDTHH:MM:SS.ffffffZZ:ZZ` | `##$ISO8601-0d0h10m0s$##` | `2023-10-25T14:50:00.156633-04:00` |
| **Epoch Unix Timestamp** | Seconds since Unix epoch | `##$Epoch-0d0h10m0s$##` | `1698245400` |

### Timestamp Offsetting Logic
- When generating an email threat lifecycle:
  1. `threatTime`: Threat identified by Proofpoint Threat Intel hours/days before (`##$TimeStamp-1d4h0m0s$##`).
  2. `messageTime`: Message received by gateway (`##$TimeStamp-0d1h15m0s$##`).
  3. `clickTime`: User clicked on rewritten URL minutes/hours later (`##$TimeStamp-0d0h30m0s$##`).
  4. `queryEndTime`: Pull execution timestamp representing current ingestion cycle (`##$TimeStamp-0d0h0m0s$##`).

## 6. Key Constraints & Pitfalls

### Critical Schema Dependencies
- **Case Variance in TAP API**:
  - Legacy or mixed TAP API responses may alternate casing: `GUID` vs `guid`, `QID` vs `qid`, `threatURL` vs `threatUrl`, and `impostorScore` vs `imposterScore`. When building SIEM validation models, adhere to the casing present in the specific schema version under test.
- **Top-Level Root Container**:
  - TAP SIEM API events are **never** delivered as naked individual message objects. They are wrapped within top-level array envelopes (`messagesBlocked: [...]`, `messagesDelivered: [...]`, etc.) with a `queryEndTime` watermark.

### Parsing & Escaping Rules
- **Angle Bracket Encoding**:
  - `headerFrom`, `headerReplyTo`, `messageID`, and envelope addresses frequently contain `<user@domain.com>`. In JSON logs, these MUST be encoded as `\u003c` and `\u003e` (e.g., `\u003cuser@domain.com\u003e`).
- **Syslog Space Quoting**:
  - In PPS Syslog lines, any field value containing spaces (e.g., `subject`, `record`, `version`, `tests`, `stat`) MUST be enclosed in double quotes (`"`).
  - Internal quotes within quoted strings must be escaped (e.g., `subject="[EXT] Re: \"Important Documents\""`).
- **Correlation Chain Integrity**:
  - An end-to-end simulated flow MUST maintain correlation across identifiers:
    - TAP JSON: `GUID` / `id` / `QID`
    - PPS Syslog: Session tracker `s=<ID>`, filter tracking token `x=<ID>-<subID>`, and MTA queue ID `qid=<MTA_QID>`.

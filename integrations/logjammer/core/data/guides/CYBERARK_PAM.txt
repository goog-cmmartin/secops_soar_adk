# CyberArk Privileged Access Management (PAM) Log Generation Guide

---

## 1. Overview & Log Purpose

### Log Description
CyberArk PAM (Privileged Access Management) logs capture security-critical activities from the CyberArk Privileged Access Security suite. This includes events originating from the **CyberArk Enterprise Password Vault (EPV)**, **Central Policy Manager (CPM)**, **Password Vault Web Access (PVWA)**, **Privileged Session Manager (PSM / PSM for SSH)**, **Event-Driven Architecture (EDA)**, and **CyberArk Identity / Dynamic Privileged Access (DPA)** cloud services.

### Monitored Activities
* **Vault Access & User Authentication**: User logon, logoff, MFA verification, failed authentication attempts.
* **Credential Lifecycle & Access**: Password retrieval (show/checkout), password usage, credential rotation (store, verify, reconcile, change) performed by PVWA users or CPM agents.
* **Privileged Session Monitoring**: PSM session establishment, protocol proxying (RDP, SSH, Database clients), real-time window title tracking, keystroke logging, executed commands, session termination.
* **Safe & Object Administration**: Creation/update/deletion of Safes, file/object permissions, category updates, policy associations.
* **Cloud & Zero Standing Privilege (ZSP)**: DPA ephemeral user provisioning, session start/end on cloud/on-prem targets, Identity SSO federated logons.

## 2. Format Specification

CyberArk PAM logs appear in multiple industry-standard formats depending on the vault translator template (`XSL` file) or cloud platform used:

```
+-----------------------------------------------------------------------------------------------+
| Log Format Variants                                                                           |
+-----------------------------------------------------------------------------------------------+
| 1. Syslog CEF (RFC 5424 / RFC 3164) -> Output of CEFSyslog.xsl (Most Common)                 |
| 2. Syslog LEEF (RFC 5424 / RFC 3164) -> Output of LEEFSyslog.xsl                              |
| 3. CyberArk EDA JSON (RFC 5424)      -> Output of CyberArk Event-Driven Architecture JSON     |
| 4. CyberArk Cloud / DPA JSON         -> REST Audit APIs / Cloud SaaS stream                   |
| 5. Vault Key-Value Syslog            -> Standard RFC5424 translator with quoted Key=Value     |
| 6. Legacy Pipe-Delimited Syslog      -> Legacy vault notification format                      |
+-----------------------------------------------------------------------------------------------+
```

### 2.1 Syslog CEF (Common Event Format)
* **Header Structure**: `<PRI>VERSION TIMESTAMP HOSTNAME CEF:0|Cyber-Ark|Vault|ProductVersion|MessageID|Desc|Severity|`
* **Extension Structure**: `act=Action suser=Issuer fname=File dvc=GatewayStation shost=Station dhost=Address duser=UserName externalId=SessionID app=Protocol reason=Reason cs1Label="Affected User Name" cs1=...`
* **Delimiters**: Pipe (`|`) separates header fields; single spaces separate extension key-value pairs; equal signs (`=`) bind keys to values.
* **Quoting Rules**: Labels containing spaces (e.g., `cs1Label="Affected User Name"`) use double quotes. Values containing spaces or special characters may be plain or quoted depending on configuration.

### 2.2 Syslog LEEF (Log Event Extended Format)
* **Header Structure**: `<PRI>VERSION TIMESTAMP HOSTNAME LEEF:1.0|Cyber-Ark|Vault|ProductVersion|MessageID|`
* **Extension Structure**: Tab (`\t`) or space-delimited `Key=Value` pairs.
* **Mandatory Keys**: `sev=`, `Action=`, `EventMessage=`, `usrName=`, `src=`, `Safe=`, `File=`.

### 2.3 CyberArk EDA JSON
* **Header**: Standard Syslog RFC 5424 header prefix (`<PRI>1 TIMESTAMP HOSTNAME`).
* **Payload**: Single-line JSON object containing `{"format":"cyberark-eda-json","version":"1.0","syslog":{"audit_record":{...}}}`.

### 2.4 CyberArk Cloud / DPA JSON
* Pure NDJSON/JSON format emitted by CyberArk Identity Security Cloud Services containing `uuid`, `tenantId`, `applicationCode`, `auditCode`, `customData`, etc.

## 3. Schema Breakdown & Fields

### 3.1 Syslog Header Fields

| Field Name | Type | Description | Example Values |
| :--- | :--- | :--- | :--- |
| `PRI` | String | Syslog Facility/Severity code enclosed in `<>` | `<5>1`, `<7>1`, `<5>`, `<13>` |
| `Version` | Integer | RFC 5424 syslog version (omitted in RFC 3164) | `1` |
| `Timestamp` | String | ISO 8601 UTC or BSD format | `2026-03-26T10:11:59Z`, `May 06 04:21:42` |
| `Hostname` | String | Vault or component hostname / FQDN | `VAULT-PROD-01`, `VAULT-NODE-PROD-02` |

## 4. Timestamp & Dynamic Time Templating

CyberArk implementations output logs in three main timestamp styles:

1. **RFC 5424 ISO-8601 UTC**: Used in modern syslog wrappers and EDA JSON:
   `2026-04-23T13:27:25Z` or `2026-04-23T13:27:25.123Z`
2. **RFC 3164 BSD Syslog**: Used in standard syslog collectors:
   `May 06 04:21:42` (Note: Single-digit days are space-padded: `May  6 04:21:42`)
3. **Epoch Milliseconds**: Used in Cloud API / DPA JSON:
   `1746455057516`

### Dynamic Generation Template Tags
When generating test data, replace all static time values with relative timestamp macros:

* **ISO-8601 Format**: `##$TimeStamp-0d2h15m0s$##` (produces `2026-04-23T13:27:25Z`)
* **Syslog BSD Format**: `##$SyslogTime-0d0h30m0s$##` (produces `May 06 04:21:42`)
* **Epoch Seconds**: `##$Epoch-0d1h0m0s$##` (produces `1774519755`)
* **Epoch Milliseconds**: `##$Epoch-0d1h0m0s$##000` or `##$EpochMs-0d0h5m0s$##`

## 6. Key Constraints & Pitfalls

### Parser Compatibility Requirements
1. **Empty Field Representation**:
   * In standard CEF logs exported by CyberArk, empty extension fields **must maintain the label pairing**, e.g.:
     `cs1Label="Affected User Name" cs1= cs2Label="Safe Name" cs2=P-SECURE-SAFE`
   * Do not drop the key name (`cs1=`) even if the value is empty, or standard SIEM CEF parsers may fail to calculate key offsets.
2. **Escaping Equals Signs in Message and Tickets**:
   * Inside CEF `msg=` or `cn2=` fields containing sub-key-value pairs, equal signs and backslashes must be escaped with a backslash:
     `msg=(Action: Connect)(Ticket ID\=INC10293)(Ticketing System\=ServiceNow)`
3. **File Path Nomenclature (`fname`)**:
   * CyberArk vault file paths follow the strict convention:
     `Root\<PlatformType>-<DeviceType/Policy>-<TargetHost/Address>-<Username>`
     *(e.g., `Root\Operating System-Dom_Windows_MAN-ad.corp.com-adm_svc`)*.
4. **Distinction Between `suser`, `usrName`, and `duser`**:
   * `suser` / `usrName` / `Issuer`: The authenticated Vault user or automation component requesting access (e.g., `PasswordManager`, `PVWAAppUser`, `john_smith`).
   * `duser` / `TargetUser` / `UserName`: The privileged managed target account whose password is being checked out (e.g., `root`, `Administrator`, `oracle_dba`).
5. **Syslog PRI Header Rules**:
   * `<5>1` represents Facility 0 (kernel/local), Severity 5 (Notice) with RFC 5424 Version 1.
   * `<7>1` represents Severity 7 (Debug/Informational).
   * Ensure there is a single space between the Syslog header and the `CEF:0` or `LEEF:1.0` declaration.
